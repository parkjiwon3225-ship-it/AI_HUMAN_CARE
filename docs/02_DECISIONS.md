# 02. 판단 기준과 의사결정 기록

> 이 문서는 "무엇을 선택했는가"보다 **"왜 그렇게 판단했는가"**를 남기기 위한 것입니다.
> 각 결정은 `결정 / 근거 / 대안 / 재검토 조건`으로 적었습니다. 새 결정은 맨 아래에 번호를 이어서 추가합니다.

## 0. 판단의 원칙 (모든 결정에 공통)

| # | 원칙 | 이 프로젝트에서의 의미 |
|---|---|---|
| A | **실제 환경에서의 일반화가 우선** | 같은 출처(같은 태블릿, 같은 대본)에서 얻은 점수는 낙관적으로 본다. 최종 판정은 실제 마이크·실제 장소 녹음으로 한다 |
| B | **문서보다 실측** | 데이터 문서(길이, 샘플레이트, 구간)를 믿지 않고 실제 파일에서 검산한 뒤 설계한다 |
| C | **지름길을 의심하고, 대조 실험으로 확인** | 점수가 너무 쉽게 높으면 모델이 쉬운 단서(말소리 유무, 음량, 패딩 등)를 쓰는지 따로 시험한다 |
| D | **기준값을 0.5로 고정하지 않는다** | 허용할 오경보율(예: 정상 소음의 1%)을 먼저 정하고, 그때의 재현율로 비교한다. 최종 오경보는 후처리까지 포함해 정한다 |
| E | **측정하지 않은 건 추정이라고 쓴다** | 숫자와 해석을 구분한다 (`(추정)`, `(확인 필요)`) |
| F | **자원을 아낀다** | 무료 GPU 한도, 업로드 용량, 시간. GPU가 필요 없는 일은 CPU에서 한다 |
| G | **재현과 중단 복구가 가능해야 한다** | 단계마다 결과를 드라이브에 저장하고, 끝난 실험은 건너뛰며 이어간다 |
| H | **공개 저장소에는 안전한 것만** | 데이터, 모델, 접속 정보, 개인 정보는 올리지 않는다 |

## 결정 목록

### D01. 음성 파트의 목표 범위
- **결정**: 위급 음성 감지 + **앞뒤 약 10초 클립을 앱으로 전달**(사람이 확인). 화자 식별은 확장 목표.
- **근거**: 오경보가 완전히 없어질 수는 없으므로, 사람이 소리를 직접 확인하는 구조가 안전하고 현실적이다.
- **대안**: 음성 인식(문장 해석) 기반 키워드 감지.
- **재검토**: 오경보가 후처리로도 허용 범위를 못 맞출 때.

### D02. 마이크 도착 전 작업 방식
- **결정**: 데이터, 모델, 파이 파이프라인, 속도 측정을 마이크 없이 먼저 하고, 파이는 **wav 파일을 마이크처럼 흘려서** 시험한다.
- **근거**: 마이크는 빨라도 11/14 이후. 도착 후에는 검증과 보정에 시간을 쓰는 게 효율적.

### D03. 학습 데이터 선택
- **결정**: AI Hub 위급상황 음성/음향(088)에서 위급 = 도움요청·응급의료·낙상, 정상 = 실내·실외.
- **근거**: 독거노인 집 안의 위급 음성이라는 목적과 직접 관련. 화재·범죄 등은 보류.
- **대안**: 직접 녹음만 사용(양이 부족), 다른 공개 데이터셋.
- **재검토**: 실제 마이크 평가에서 성능이 부족할 때 직접 녹음 비중 확대.

### D04. 다운로드 방식과 범위
- **결정**: 선택 다운로드(필요한 클래스만), Training과 Validation 모두. 큰 파일은 웹 이어받기 도구 사용.
- **근거**: `aihubshell`은 중단 시 받던 파일 삭제, 임시 디스크 2~3배 필요. 코랩 업로드 용량(드라이브 무료 약 15GB)도 고려.

### D05. 오디오 변환 규격
- **결정**: **16kHz 모노**, 헤더의 실제 샘플레이트 기준으로 변환, **4초 창**으로 저장(int16).
- **근거**: 말소리 정보 대부분이 8kHz 이하. 입력이 작아 파이에서 가볍다. JSON의 "44.1kHz"는 신뢰할 수 없음(실측: 44.1/48/96kHz 혼재).
- **대안**: 44.1kHz 유지(저장·계산 3배, 효과 불확실).
- **재검토**: 비언어 소리(쿵, 유리 깨짐)를 다룰 때 고주파가 필요한지.

### D06. 클래스 구성
- **결정**: 낙상 + 도움요청 + 응급의료를 **하나의 "위급 말소리" 클래스**로 합친다 (원래 이름은 메타 파일에 보관).
- **근거**: 알림은 "위급 여부"만 필요. 세부 구분은 사람이 클립을 들으면 된다.
- **재검토**: 앱이 세부 종류를 필요로 할 때.
- **참고**: 낙상 데이터는 쿵 소리가 아니라 "넘어졌어요" 같은 **말소리**가 이벤트 구간. 낙상 충격음 감지는 별도 모델/출력 후보로 보류.

### D07. 짧은 클립 처리
- **결정**: 변환 단계에서는 반복으로 채워 4초를 만들되, **학습에서는 반복 구간을 쓰지 않고 실제 소리 구간에서만 2.5초**를 자른다. 2.5초 미만(약 5%)은 제외.
- **근거**: 무음으로 채우면 "무음 패딩 = 위급"이라는 지름길이 생긴다. 반복으로 채운 창은 청취 시 어색하고 반복 패턴이 새 단서가 될 수 있다.

### D08. 샘플링 규칙
- **결정**: 문구(note)당 최대 40클립, 정상은 소음 종류(note)별로 돌아가며 선택, 위급:정상 창 수 1:1.
- **근거**: 낙상의 47%가 "미끄러졌어요" 한 문구. 균형을 맞춰 한 문구·한 배경에 쏠리지 않게.

### D09. 모델 구조
- **결정**: 로그멜(64 멜 × 251 프레임, 10ms 간격) → 3×3 합성곱 4블록(16-32-64-64) → 전역 평균 → 선형. **6만 파라미터**. 입력 2.5초.
- **근거**: 라즈베리파이에서 실시간으로 돌릴 크기. 이미지 대비 연산량이 매우 작음([04](04_MODEL_EXPERIMENTS.md)).
- **재검토**: 실제 마이크 평가에서 모델 용량이 병목일 때.

### D10. 입력 정규화와 증강
- **결정**: 창마다 로그멜을 평균·표준편차로 표준화, 위급 클립에 정상 소음을 SNR 0~20dB로 얹기(60%), 음량 ±12dB 무작위, SpecAugment.
- **근거**: "위급은 크고 깨끗하다"는 단서(음량, 배경)를 줄이기 위해.
- **한계**: 표준화는 소리가 매우 작을 때 잡음을 키워서 조용한 입력의 오경보를 올림(-40dB에서 9%) → 실제 장비에서는 **소리 크기 게이트**로 보완.

### D11. 평가 원칙
- **결정**: (1) 정상 소음 오경보 1% 기준 재현율, (2) 하위 그룹(클래스, 길이, 음량, 거리, 문구)별 분해, (3) 소음 크기·말소리 길이·위치·음량 탐침, (4) 합성음 시험, (5) 문구·연령 홀드아웃.
- **근거**: 원칙 C와 D. 같은 출처의 평균 점수만으로는 지름길을 알 수 없다.

### D12. 일상 말소리를 정상에 추가 (v1)
- **결정**: Zeroth-Korean(CC BY 4.0) 낭독 음성을 정상으로 추가. 소음을 섞어서(70%) 위급 클립과 환경을 맞춤. 시험 화자는 학습 화자와 분리.
- **근거**: v0가 일반 말소리를 94.5%(기준 0.5) 위급으로 판단. 정상에 말소리가 없던 것이 원인.
- **한계**: 낭독은 실제 대화·TV와 다르고, "읽는 말투 vs 연기 말투"를 배웠을 가능성이 있음.
- **재검토**: 마이크 도착 후 TV·라디오·대화를 직접 녹음해서 추가.

### D13. 모델 선택 시점
- **결정**: v0는 검증 AUC가 가장 높은 에폭(18번째), v1과 실험들은 마지막 에폭을 사용.
- **근거**: 검증 세트로 에폭을 고르면 점수가 약간 낙관적이 된다. 실험 비교에서는 선택 편향을 없애기 위해 마지막 에폭으로 통일.

### D14. 코랩 운영 방식
- **결정**: GPU가 필요 없는 작업(다운로드, 변환, 진단)은 **CPU 런타임**, 학습만 **GPU**. 실험마다 모델과 결과를 드라이브에 즉시 저장하고 끝난 실험은 건너뛰며 이어서 실행. 노트북 A/B/C로 분리.
- **근거**: 무료 GPU 한도는 비공개·변동.
- **유료 플랜**: 지금은 불필요. 마이크 후 막히면 **Pay As You Go 일회 구매**(구독 아님, 유닛 90일 유효)를 검토. 자세한 내용 [06](06_COLAB_RUNBOOK.md).

### D15. 파이 배포 방식
- **결정**: **ONNX + numpy 특징 추출**(PyTorch는 파이에 설치하지 않음), 파이썬 가상환경(venv).
- **근거**: 가볍고 설치가 쉽다. 학습 쪽 PyTorch와의 결과 동일성을 검산(차이 7e-06 / 2e-07).

### D16. 기준값과 후처리
- **결정**: 기준값은 0.5로 두지 않고 **허용 오경보율에서 정한다**. 후처리로 (1) 연속 N회 감지, (2) 소리 크기 게이트, (3) 알림 후 쉬는 시간을 둔다. 값은 실제 마이크 데이터로 정한다.
- **근거**: 판단을 초당 한 번 한다면 하루 86,400번이라, 오경보율 1%도 하루 약 860번. 후처리 없이는 쓸 수 없다.

### D17. 저장소 공개 규칙
- **결정**: 데이터, 학습된 모델, 키, IP, 계정, 와이파이 이름, 팀원 개인 정보는 올리지 않는다 (`.gitignore`, `<PLACEHOLDER>`).
- **근거**: 저장소가 공개 상태이고, AI Hub 데이터는 재배포가 제한된다.

### D18. 평가는 연속(스트리밍) 조건의 시간당 오경보와 이벤트 감지율로 (2026-11-03)
- **결정**: 모델과 규칙의 비교 기준을 "창 단위 재현율"에서 **연속 스트림에서의 시간당 오경보 + 위급 이벤트 감지율 + 감지 지연**으로 바꾼다.
- **근거**: 창 단위 재현율 0.93이 연속 환경에서는 오경보 목표를 지킬 때 0.26이었다(원칙 A, D).
- **재검토**: 마이크 후 실제 녹음으로 스트림을 만들 수 있을 때.

### D19. 오경보 허용 수준은 팀이 정한다 (2026-11-03)
- **결정**: 합의 전까지는 임시 목표(소음 시간당 1회 이하, 말소리 3회 이하)로 비교한다. 실제 목표(하루 몇 회)는 팀 합의 후 확정.
- **근거**: 시간당 1회도 하루 24회라서, 하루 5회 이하를 원하면 지금 모델로는 불가능하다.

### D20. 긴 코드는 파일로 전송한다 (2026-11-03)
- **결정**: 파이 터미널에 긴 스크립트를 붙여 넣지 않고, 파일로 받아 `scp`로 보낸다.
- **근거**: 붙여 넣기에서 코드 중간이 사라졌다(코랩에서도 약 10,300자에서 잘린 적이 있음).
